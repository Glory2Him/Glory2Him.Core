# Content item engagement
Parent: [Likes.md](../../Likes.md)
Level: hook — `useContentItemEngagement` (`Websites/Glory2Him.WebApp.React/src/hooks/useContentItemEngagement.ts`), the engagement wiring every page that renders the card shares
Inherits: §ARC16.8 (*Where each shared rule lives*, *The projection*), §UI20.6.6 rule 2, `UI/Components/ContentItemPanel.md rules 3.1.8 and 3.2.4`, Likes.md rules 1–7

Seven pages take their card's engagement from this hook (`home.tsx`, `posts.tsx`, `postDetail.tsx`, `myPosts.tsx`, `myPostDetail.tsx`, `admin/contentItemModerationPage.tsx`, `admin/contentItemModerationDetailPage.tsx`). Today it keeps a chosen reaction in page state for the visit and reads nothing but the vocabulary. The page decides what follows the card's hook (`UI/Components/ContentItemPanel.md rule 3.2.4`), and this hook is how every page decides it the same way. Its other members, `reactionOptions`, `onShareClick` and `onSaveClick`, are unchanged here. Each option gains the reaction's `id` in its own projection (`UI/Views/ContentItemReactionOption.md §1`).

**There is one tally, the server's** (§ARC16.8, *Which reaction this viewer holds*). What the reader sees between their press and the read that follows the item's latest write is an optimistic overlay on the element — the reaction pressed and the counts moved — and that read replaces it wholesale (§2 rule 8). It is never a second store kept in step with the first.

## 1. withReactions — the counts and the reader's own reaction on each card (#738)

1. **The page hands the hook the ids of each page of cards it has delivered** — a list page its delivered pages, a detail page one page of its one id — and the hook reads their summaries through `associationService.useGetReactionSummaries` (`UI/Foundations/AssociationService.md §3`), handing it the reader from `useAuth`: `undefined` while there is no current user, because its read is still loading or failed; `user.userId` once the current user is authenticated; and `null` once the current user has been read and is not authenticated (§3 rule 4), so the set is keyed on what was delivered and never on the accumulated list (§ARC16.8, *The set, its bounds*).
2. **`withReactions` projects each summary onto its element**, in place of today's `withViewerReactions`: `reactionSummary` gets one entry per reaction, in the summary's order — the reaction's `name` as its `label`, its `unicodeEmoji` as its `glyph`, and its `count` — and `viewerReactionLabel` gets `viewerReactionName`. Renaming into the view's vocabulary is this layer's (§ARC16.8, *The projection*).
3. **An element with no summary shows no counts and no pressed reaction**, and still offers Like: its read has not landed, its page's read failed, or the server did not answer for it (§ARC16.8: an id the read cannot answer for is absent). A card is never shown another item's counts.
4. **The overlay is §2's.** This section projects the summary alone, and §2 lays the reader's pending choice over it.

## 2. onReactionSelected — give, change or withdraw (#739)

1. **While the reader is not yet known, a choice does nothing**: the reader is not sent to sign in, and nothing is recorded (§UI20.6.6 rule 2). Today the card holds the first half of this guard, for a reader still being read (`contentItemPanel.tsx`, the `onReactionSelected` handler), and sends a reader whose read failed to sign in; this rule changes that. The reader is not yet known while their sign-in state is still being read, and when its read failed (§1 rule 1). A failed read has already been announced by the app's global handler (`apiBroker.globals.ts`), so the choice adds nothing to it.
2. **A signed-out reader is sent to sign in**, through the one reusable sign-in action, and returned to exactly where they were (`UI/Pages/Home.md §6 item 3`; Likes.md rule 4).
3. **A signed-in reader who chooses a reaction they do not hold gives it** — or changes to it, where they hold another — through `associationService.useUpsertAssociation` (`UI/Foundations/AssociationService.md §1`), the item as endpoint A and the reaction as endpoint B.
4. **A signed-in reader who chooses the reaction they hold withdraws it**, through `associationService.useRemoveAssociationByPair` (`UI/Foundations/AssociationService.md §2`). Which reaction they hold is the element's `viewerReactionLabel`, as §1 and the overlay leave it.
5. **The overlay moves at once.** The chosen reaction is pressed, or none after a withdrawal. The counts move as `UI/Views/ChosenReactionSummary.md §1` computes them from the item's summary and the hook's `reactionOptions`, which are in the vocabulary's order (`UI/Brokers/ReactionBroker.md §1`).
6. **Any failed write takes the item's overlay away**, whichever of the item's writes it was: the only one, the first, the latest or one between. It takes its own overlay and any overlay a later choice laid over it, because that started from it, and it never restores an earlier choice's overlay. The card shows what the last read said. The failure is announced as every failed write is, by the app's global handler, and the hook raises no toast of its own. When a write settles either way, the summaries are read again (`UI/Foundations/AssociationService.md §1`), and rule 8 says which read replaces the overlay.
7. **The reaction's id travels on the option**, which `UI/Views/ContentItemReactionOption.md §1` builds. The option's `label` stays its identity everywhere else (`contentItemSearchItem.ts`).
8. **The overlay lies over the summary until the read that follows the item's latest write replaces it.** `withReactions` shows it on top of the item's summary. When a write settles, whether it succeeded or failed, the hook waits on `associationService.useReadReactionSummariesAgain` (`UI/Foundations/AssociationService.md §4`). When that wait ends, the read that follows the write has landed, and the hook drops the item's overlay if that write is still the item's latest. That read counts even when it answers exactly what the last read did. Every other read leaves the overlay in place: one already in flight when the reader chose, one another card's write started, one the write's own refresh sent before the write settled, and the read that follows an earlier write on the item. Apart from a failed write, which takes it away at once (rule 6), nothing else drops it.
9. **A choice made while an overlay stands starts from that overlay**: its counts, and the reaction it left held, which decides whether the choice gives, changes or withdraws (rule 4). The first choice's change is carried forward, never counted twice or left behind, and a second press of the same reaction withdraws it.
10. **Each write's outcome comes from its own call, and each item's overlay is its own.** One `useUpsertAssociation` and one `useRemoveAssociationByPair` serve every card on the page. TanStack Query reports only a mutation's latest call through its shared state and through the callbacks passed to `mutate` (TanStack Query, *Mutations*, consecutive mutations). So the hook reads each write's success or failure from the promise `mutateAsync` returns for that call, and keeps each item's overlay and pending writes apart. A write on one card never ends, keeps or changes another card's overlay (rules 6 and 8). The handlers the mutations declare themselves run for every call, so the read after every write still happens (`UI/Foundations/AssociationService.md §1`).
