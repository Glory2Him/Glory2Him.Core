Berean is the reviewer a moderator can ask onto a round, or that a policy assigns to it. Assigning it starts its review: the review process records a confidence score and a reason on the item under review, may file comments, and casts Berean's vote where the policy lets it. Berean's row on the round shows whether that review is pending or complete. While Berean is assigned, the round waits for its review to start and to finish, and a score below the rejection threshold can hold the round's final approval shut until somebody bypasses it.

## Problem

Berean was designed to vote: to file an `ApprovalReview` decided from a confidence score against two thresholds (§APR8.6.2 rules 1–3). A publisher or administrator could set or correct that score by hand (§APR9.7.1 rule 5), only an `Association` carried one (§APR8.6.2, *`ContentItem` is deliberately not scored*), and the only block on it was a score of exactly zero (`BlockOnZeroApprovalScore`, §APR8.5 rule 8). None of the voting was built, and nothing ever completed Berean's review: its assignment's two flags had no writer (§APR8.6.2, *Trigger event — NOT built*). The owner ruled on 2026-10-13 that no person sets a score, that every approvable item is scored, and that a low score, or a score Berean still owes, holds the round. On 2026-10-14 the owner kept Berean's vote, gave its assignment a recorded start and completion, and set out the approval process a data change runs.

## The rulings

The owner ruled on 2026-10-13, in their own words. Rulings 1–3 are #1117's, and the answers A1–A7 are to #1117's open questions 1–7. Where a later ruling below differs, the later one applies, and *What they supersede* names each.

1. *"non-system users will NOT be able to set it [the confidence score/reason] by hand. They cast their vote based on their own confidence (or by factoring in what Berean answered). Berean is assigned as an AI reviewer, but it can't actually vote itself. With it being requested as a reviewer, it triggers the confidence process which then gives its confidence score and reason. The only outcome from the Berean reviewer is an indicator status: Requested / busy (isAIReviewCompleted false): a yellow filled dot (bi-circle-fill text-warning) with the tooltip 'Berean's review is pending'. It replaces the 'Requested' badge a human reviewer would get. Completed (isAIReviewCompleted true): two glyphs on the same line. A recycle icon (bi-arrow-repeat) is a button with the tooltip 'Re-request Berean review'; it raises onAIReviewerRequested. A chat-bubble icon (bi-chat-dots) is blue with 'Berean left review comments' if there are comments, and muted grey with 'Berean left no comments' if there aren't."* The recycle button is withdrawn by A7, and *"it can't actually vote itself"* by I2.A.
2. *"If Berean is enabled, it will trigger the confidence process the moment something comes in that requires review (excluding things that are auto approved i.e. Likes). If Berean is NOT enabled, the confidence process will not start and therefore the values will remain NULL."* Read with R2 below: *the moment something comes in* is the moment Berean is assigned to it, manually or automatically, and not the moment its round opens. A round whose tier offers Berean with the automatic switch off is not scored until somebody adds Berean.
3. *"The confidence process has its own thresholds. The shipped Berean thresholds are 2.50 for rejection and 7.50 for approval. They sit on the 0.00–10.00. … If Berean is enabled, then these values will weigh into the voting, i.e. a low score may prevent final approval UNLESS bypass is used."*
- **A1 — where the thresholds live:** *"This already lives on ApprovalSetting"*.
- **A2 — what *enabled* is:** *"ApprovalSetting.IsAIReviewerOffered = true"*. **Which rounds are skipped:** *"ApprovalSetting.RequireApprovals = false OR ApprovalSetting.IsPersonal = true. Both these will not require a review round so Berean's confidence process should not be started on them."*
- **A3 — the block:** *"Lets rename `ApprovalSetting.BlockOnZeroApprovalScore` to `ApprovalSetting.BlockOnRejectApprovalScore`. If `ApprovalSetting.BlockOnRejectApprovalScore` is boolean field has a true value, then the rules must block approvals. The only way to get past this is to use the bypass feature. If `ApprovalSetting.BlockOnRejectApprovalScore` is false, then this advisory is NOT enforced. The gate will compute this value as a boolean value based on the applicable ApprovalSetting -> `BlockOnBelowBereanRejectionScore` = Berean confidence score <= ApprovalSetting.AIApprovalConfidenceRejectionThreshold"*. Its *<=* is replaced by I4.1's strict comparison.
- **A4 — what is scored:** *"Anything that is subject to approval will get the option of adding Berean as a reviewer. If ApprovalSetting.IsAIReviewerOffered = true, then Berean can be added as a reviewer either manually or via ApprovalSetting.IsAIReviewerAutomaticallyRequested = true. This will trigger the confidence process that will then record a confidence score and reason against the approval. The confidence score and reason will always be there BUT what is scored will depend on the type of approval. … We still need to build the confidence process, but the outcome is uniform and generic for all. If the confidence score is <= than what is recorded on ApprovalSetting.AIApprovalConfidenceRejectionThreshold then the gate MUST block the approval if ApprovalSetting.BlockOnRejectApprovalScore = true, otherwise the score and reason will just be visible warning on the UI."* **Corrected the same day:** *"It is recorded against the entity that implements IApproval since IApproval implements IConfidence … Association must not implement IConfidence again since it is getting it via IApproval"*, with the target declaration `public interface IApproval : IConfidence { … }`, its existing members unchanged. The owner's examples of what each type is judged on — a content item's theme, a tag's language and spelling, a Bible reference's existence and its quoted text, an association's pairing — are examples, not rules: what is judged is the review process's (#1216).
- **A5 — comments:** *"That will depend on the confidence process. I would think in general the confidence process will only do the score and reason for the score. But we might do the confidence process and decide we want to also submit comment or question than may need resolution i.e. submit a question that will block the review round …"*
- **A6 — a null score:** *"If Berean is assigned as a reviewer, then a null score MUST block the approval to allow the confidence process to complete. If Berean is not assigned as a reviewer, then the null score MUST not block the review round as it simply means Berean was not required."*
- **A7 — re-runs:** *"A score on unchanged content never changes. From a UI perspective, you cannot request a re-review. The UI will only show Requested and then the status of where the confidence process / Berean are. If a review round is cleared as dismissed due to a change, then Berean can be manually added which will then trigger a re-review OR when the round is cleared as dismissed but Appsetting.IsAIReviewerAutomaticallyRequested = true, then the approval MUST automatically add Berean for the new round (verify this happens today). Following this, users cannot abuse the re-review to force a new score or stack up costs for AI reviews."*

## Business rules

1. **No person sets a confidence score or reason.** The four `IConfidence` fields — `ConfidenceScore`, `ConfidenceReason`, `SourceBatchId`, `ModelVersion` — are written only by the system identity, through each entity's set-confidence operation (§APR9.7.1 rule 5): the review process records them (rule 6), and the approval process clears them on a data change (rule 9). Every other caller is refused there, `Publishers` and `Administrators` included, and an item's add and general modify never accept them (§APR9.7.1 rule 2). *(ruling 1)*
2. **Every approvable entity carries a score and a reason.** `IApproval` extends `IConfidence`, so `ContentItem`, `Link`, `Tag`, `Reaction`, `Comment`, `BibleReference`, `Attachment` and `Association` all carry the four fields, and `Association` no longer declares `IConfidence` itself (§APR9.7.1 rule 5). The score sits on the item, not on its round: a round is the item's approval, and what the score judges is the item. **A score blocks only the item it is on** (I1.2): that item's round, and no other. `Attachment` has no round of its own (§APR7.5.1 rule 5), so its fields stay null. *(A4, as corrected; I1.2)*
3. **Berean is offered where the round's resolved policy offers it and requires review.** It is offered where the resolved `IsAIReviewerOffered` is `true`, `RequireApprovals` is `true` and the item is not a personal association — one whose `UserId` is set, which is what the policy key's `IsPersonal` reads (§APR8.4) — on every approvable entity type that has a round (rule 2). Everywhere else it is not offered, cannot be asked, is never assigned automatically, and nothing it does is performed (§APR8.2, the `IsAIReviewerOffered` row). A Like's round is skipped on both counts: the seeded personal tier has `RequireApprovals = false`, and a Like is a personal association. The item's own personality is read, as I3.1 step 4.2 names it (*"an association with `IsPersonal == true`"*), rather than the key of the row that resolves, which A2 names; the two differ only for a personal association no personal tier governs. Such a round is approved as it opens (rule 22), and the offer's two terms are what keep it so: without them the approval process's step 4.2 (rule 9), or §APR8.6.2.1 gate 4 while its subscription stands, would assign Berean to the round before the evaluation that approves it, and once the gathers ship (*What ships together*, step 4) the pending block would hold it (rule 11). A person's request meets the two terms only on a round still open to it: one open before rule 22 shipped, one the administrators' reset re-opened (rule 23), or one whose resolved policy stopped requiring review while it stood open, since nothing re-tests a round on a change to the approval settings (*Risks*). *(A2, I3.1)*
4. **Berean's review starts on the review event, and on nothing else.** Berean is assigned by a person's request (`POST`, §APR8.6.2, *Assignment*) or by the approval process, where the resolved policy offers Berean and asks for it automatically (rule 9, step 4.2). Once either has run, it publishes `AIReviewerOrchestration-Reviewing` once, carrying the round's live assignment, wherever Berean is then assigned to a round that still offers it (rule 3) — whether it was assigned just then or stood from before — and nowhere else (I3.1 step 4.3, I5.1, I6, I7, R9). So a person who asks for Berean while it stands assigned publishes the event again (I7), and a request that failed publishes nothing. **On a round that no longer offers Berean nothing publishes it**, though Berean may stand assigned there from before: a person's request is refused by the offer before it reads the assignment, and step 4 removes Berean instead (rule 9, step 4.3; R9). **Only a person's act publishes it**: a person's request, or step 4 on an add or an update a person made. Nothing the system writes publishes it, the administrators' reset among them (rule 23): a fact the system causes re-tests the round's blocks, and starts no review and no vote (R4). That event is the one start: an assignment's own `-Added` fact starts nothing, so an assignment and its event are never two starts (I5.1), and there is no re-request (rule 8). The review process that hears the event is designed under #1216 (I3.8). A round whose tier offers Berean with the automatic switch off has no review until somebody adds Berean (R2). *(ruling 1, A4, A7, R2, R4, R9, I3.1, I5.1, I6, I7)*
5. **Berean votes where the policy lets it.** Where the resolved `IsAIAllowedToVote` is `true`, the review process casts Berean's vote last, once the score is recorded (I2.A): `Approved` where the score is above the resolved `AIApprovalConfidenceApprovalThreshold`, `Rejected` where it is below the resolved `AIApprovalConfidenceRejectionThreshold`, and no vote where it lies between them or on either (I3.1, I4.1). A null score reads as `0.00`, so it is a `Rejected` vote wherever the rejection threshold is above `0.00` (I3.5). The vote is an `ApprovalReview` and counts as a person's does (I3.2): toward `RequiredNumberOfApprovals`, so on a tier that needs one approval it alone meets the count, for a manual approve with no bypass or, where `AutoApproveIfAllApprovalRequirementsMet` is on, the automatic approval (I4.3); and as a rejection, which ends the round where `BlockOnReject` is on (§APR8.7 rule 1). Where `IsAIAllowedToVote` is `false`, Berean casts no vote. How the vote is filed is the review process's (#1216). `IsAIAllowedToVote`, `CK_ApprovalSetting_AIVoteRequiresAIReviewer` and the seed's `false` stay. *(I2.A, I3.1, I3.2, I3.5, I4.1, I4.3. This rule used to read "Berean casts no vote", under ruling 1.)*
6. **What the review process does is designed under #1216.** The owner's outline is its requirement (I2): where the item holds no score, it runs the strategies that fit the item's type, records the score and the reason they give through set-confidence, posts any comment or question a strategy asks for to the round's thread, and records where the review stands on the assignment (rule 21); where the item already holds a score, it skips the scoring; and it votes last where rule 5 lets it. The strategies are an orchestration's list, filtered by the item's type, every matching one run, the vote always last (I3.8). A comment it files may be a settled remark or an outstanding question, which holds the round shut while `RequireReviewCommentResolutionBeforeApprovals` is on (§APR7.8, §APR8.5 rule 7), and a question Berean files is settled on its behalf by the publisher tier (§APR8.5 rule 7, route 2), since Berean is not a person who can settle it. *(A5, I2, I3.7, I3.8)*
7. **A score on unchanged content never changes.** Set-confidence writes a score only onto an item that has none, and leaves a stored score as it is, and the review process skips the scoring where a score stands (rule 6). Only rule 9's data change clears one: a dismissal that is no data change, a withdrawal and an assignment leave it as it is (I1.4, I1.5c, I2.D). *(A7, I1.4, I2.D)*
8. **Berean's row shows where its review stands, and offers nothing else.** While the assignment's review has not completed (`IsAIReviewCompleted` is `false`), started or not, a yellow filled dot (`bi-circle-fill text-warning`) with the tooltip *"Berean's review is pending"* stands where a person's *Requested* badge would. Once it is complete, a chat-bubble (`bi-chat-dots`) stands there: blue, with *"Berean left review comments"*, where the assignment's `IsAIReviewCommentsPresent` is `true`, and muted grey, with *"Berean left no comments"*, where it is `false` (I1.6). There is no re-request control (`UI/Components/ReviewPanel.md` rule 2.45). *(ruling 1, A7, I1.6)*
9. **A data change runs the approval process's four steps.** A data change is an add, or a modify that changes a content field, by the test §APR8.6.3 rule 3 applies to the amender record. An echo of the stored row changes none, and neither does a status move between `Draft` and `Submitted` alone (R1). On a data change the approval workflow, under the system identity (rule 19):
   1. **dismisses reviews.** Under `RequireReapprovalOnChange = true` it dismisses the round's active reviews (§APR8.8 rule 1), Berean's vote among them, and Berean's live assignment with them: Berean is not on the round after a data change (I3.1 step 1, I3.3). Under `false` it dismisses only Berean's vote, where Berean cast one, so that Berean acts on its own finding (I5.2); Berean stays assigned, and the people's reviews stand (§APR8.6 residual 1). The vote, and so its dismissal under `false`, is built under #1216;
   2. **clears the score.** The item's four `IConfidence` fields are cleared, under either setting: the data they judged has changed (I2.C, I3.1 step 2, I3.4);
   3. **clears Berean's review.** The assignment's five tracking fields (rule 21) are cleared, under either setting: on the assignment that stays live under `false`, and on the one dismissed under `true`, in the dismissal's own write (I3.1 step 3);
   4. **runs the approval process** on a round that stands `Submitted`. This step runs on every add and every update a person makes to an item whose round stands `Submitted`, a data change or not — an edit, an echo, a submission from `Draft` — and on nothing the system writes, the reset's re-opening among them (I3.1 step 4; R4; rule 23):
      1. a round that requires no review is approved (rule 22);
      2. where the resolved policy offers Berean and asks for it automatically, and no live assignment stands on the round, Berean is assigned: an upsert, since under `false`, or on an update that is no data change, it may stand already (I3.1 step 4.3.1, I4.2). So on the round a data change opens under `true`, whose Berean assignment step 1 dismissed, Berean is assigned only where the policy offers it and asks for it automatically, however Berean came onto the round before (R3);
      3. where Berean is then assigned and the round still offers it (rule 3), the review event is published once (rule 4; I5.1, I6, I7). Where Berean stands assigned on a round that no longer offers it, no event is published, and Berean's live assignment is removed, under the system identity (rule 19; R9);
      4. the round is evaluated, and only a round no condition blocks is approved, manually or automatically; a bypass gets past a block, and otherwise the block must be resolved (I3.1 step 7).

   **What step 4.3's removal reaches (R9).** The owner was asked of a round whose switch was turned off, or which stopped requiring review, and answered *"remove Berean because IsAIReviewerOffered is now false"*. The offer step 4 reads is the one rule 3 composes, `IsAIReviewerOffered` with the round requiring review, so it is false on both rounds the question named, and on a round Berean was given before rule 3's terms shipped, which never required review (rule 22): the removal reaches all three. Step 4.2 never assigns Berean where the round no longer offers it, so the assignment removed always stood before the flow. The removal is the system's act and no person's withdrawal, so rule 18's refusals are not asked of it, and it is a reviewer change and no data change, so the assignment's five tracking fields and the item's score stay as they are (rules 7 and 21). It removes Berean whatever its review has reached, the owner's reason being the closed offer, and the blocks that ask for Berean assigned go with the assignment:
   - **the pending block** (rule 11) lifts, which is the effect the owner named: *"it will also not look like Berean is pending on that round while it will never fire"*;
   - **the in-flight block** (rule 11) lifts. The review is not cancelled: it runs on, as it runs on past a bypass (I1.5a; I1.5c, *"we cant cancel"*), and what it does with an assignment removed under it is #1216's (rule 17). The round can then be decided before that review completes;
   - **the low-score block** (rule 10) lifts, since it holds only where Berean is assigned, so a score below the rejection threshold, a missing one included, is a warning a moderator reads, as on any round Berean is not on, and as ruling 3 has the thresholds weigh in *"If Berean is enabled"*.

   What becomes of a vote Berean has cast on the round is #1216's, with the vote (rule 5). **Only step 4 removes Berean, so only a person's add or update does** (R4): a fact the system causes re-tests the round and removes nothing, so until a person's next add or update Berean's blocks still hold such a round (rule 22), and a person may withdraw Berean while its review has not started, since a round that no longer offers Berean does not ask for it automatically (rule 18). The administrators' reset reaches no step 4, so it removes nothing, and Berean stands on the round it re-opens as it was (rule 23; R5). **R4 and R5 stand with it**: the removal runs only inside a person's add or update, starts no review and no vote, and its `AIReviewerAssignment-Removed` is a fact the round re-tests, which R4 has *"resolve blocks on the gates"*; and the reset, which R5 governs, never reaches it.

   **The owner's order holds, with steps 4.1 and 4.4 in one evaluation.** A round that requires no review is never offered Berean (rule 3), so step 4.2 assigns nothing on it and step 4.3 publishes nothing, and the evaluation that approves it (rule 22) can be the one that runs last. Where Berean stands assigned on such a round from before, step 4.3 removes it, so that evaluation approves it too (R9). **An assignment the round gains during the flow is the new round's, and is neither dismissed nor doubled.** Until the automatic assignment's subscription on `Approval-Modified` is retired (`Backend/Orchestrations/AIReviewerOrchestrationService.BereanReview.md §6`), it hears the `Approval-Modified` of a `Draft` round the flow moves to `Submitted` (§APR9.2 rule 3, §APR8.6.2.1), inside that move's publish, because delivery is synchronous (§EVN11). So step 1 dismisses the assignment that was live when the flow began, and step 4.2 finds the new one live and adds none. **Every dismissal comes before every write the round re-tests**, so that no re-test inside the flow counts a review the flow is about to dismiss (`Backend/Orchestrations/ApprovalOrchestrationService.BereanReview.md`, *Order in the Modified flow*).

   **Nothing else clears Berean's review.** Not an echo, nor a status move alone (R1); not a dismissal that is no data change, such as §APR8.6 HR-4's reset, which re-opens the same content, leaves the score and the assignment as they stand, and fires nothing (rule 23; I1.4, I2.D, R4); not a withdrawal (rule 18); not an association's `-Modified`, which can carry no content (§APR7.5.1 rule 4); and not the dismissal of an amender's own review (§APR8.6.3 rule 7), which comes with a data change that runs these steps anyway. A changed reaction is a personal association's, whose round is approved by rule 22 and never offers Berean (rule 3). **The flow cannot yet tell a data change from an echo.** Every modify publishes `-Modified`, an echo included, and the fact carries the row after the write, never the row before it; only a service that writes the item sees both. For a `Tag`, a `Reaction`, a `Comment` or a `BibleReference` that is the item's foundation, whose `-Modified` the flow hears. For a `ContentItem` or a `Link` the flow hears the processing tier's fact, `ContentItemProcessing-Modified` or `LinkProcessing-Modified` (`ApprovalOrchestrationService.Substrate.cs`), and that service reads the stored row before it modifies or forks (`ContentItemProcessingService.cs`, `LinkProcessingService.cs`). How the answer reaches the flow, on whichever fact it hears, is designed under #1215, and steps 1–3 wait for that design (*What ships together*, step 6). *(A7, R1, R3, R4, R9, I2.C, I3.1, I3.3, I3.4, I4.2, I5.1, I5.2, I6, I7)*

   **What happens today, checked on `main` at a3943d8a, as A7 asked.** Both paths that dismiss — the Modified flow under `RequireReapprovalOnChange = true` and HR-4's reset — return a live, completed assignment to pending, through `IAIReviewerAssignmentWorkflowService.ReturnStaleAIReviewerAssignmentToPendingAsync` (`ApprovalOrchestrationService.Flows.cs:192-197`, `ApprovalOrchestrationService.AIReviewer.cs:98-124`), whatever `IsAIReviewerAutomaticallyRequested` resolves to. Neither adds Berean where it was never assigned or was withdrawn: the reset's helper finds only a live, completed row (`AccessBroker.FindResettableAIReviewerAssignmentIdAsync`), and the automatic assignment hears `Approval-Added` and `-Modified` alone, whose gate 6 stands down wherever any assignment row exists (§APR8.6.2.1). Because nothing completes an assignment today, no assignment is ever completed, so in practice neither path changes anything. Rule 9 replaces both behaviours.
10. **The low-score block.** `BlockOnZeroApprovalScore` is renamed `BlockOnRejectApprovalScore`. Where it resolves `true` and Berean is assigned to the round, an item whose score is below the round's resolved `AIApprovalConfidenceRejectionThreshold` cannot meet the §APR8.5 conditions, on the automatic approval and the manual approve alike, and only a bypass gets past it (§APR8.6 HR-4 route 3). A null score reads as `0.00` (I3.5), so it is below any rejection threshold above `0.00`. A score on the threshold is not below it (I4.1). Where the setting resolves `false`, or Berean is not assigned, the score blocks nothing and is a warning a moderator reads. *(A3, A4, I1.5b, I3.5, I4.1)*
11. **Berean's review holds the round until it has completed.** While Berean is assigned to a round — it holds a live assignment — its review blocks the §APR8.5 conditions, whatever `BlockOnRejectApprovalScore` says and on every tier (I1.5a, I2.F), by one of two values computed from the assignment and never stored:
    - **`IsAIReviewPending`** — Berean assigned and `IsAIReviewStarted` `false` — blocks with *"The Berean review has not started."* (I2.F, I3.6);
    - **`IsAIReviewInFlight`** — Berean assigned, `IsAIReviewStarted` `true` and `IsAIReviewCompleted` `false` — blocks with *"The Berean review has not completed."* (I1.5a).

18. **Withdrawing Berean.** A person may withdraw Berean only while its review has not started (`IsAIReviewStarted` is `false`) and the resolved policy does not ask for Berean automatically (I1.5c, I2.B): a started review is a process that cannot be cancelled, and an automatically requested Berean is required by the policy, so removing it takes a change to the policy (I2.B). The automatic request is read as the offer verdict composes it, `IsAIReviewerOffered && IsAIReviewerAutomaticallyRequested` (§APR8.6.2.1 gate 4), because the automatic switch has no effect without the offer (§APR8.6.2 setting 3). A withdrawal is a reviewer change and no data change: it changes no tracking field and no score, so withdrawing and asking again buys neither a different score nor a second run's cost (I1.5c). It lifts rule 11's pending block. *(I1.5b, I1.5c, I2.B. It used to be unconditional, and to keep the score as its only effect beyond the block.)*
19. **Every write the workflow makes for Berean is the system's own.** The approval process's dismissals, clears and assignment, the review event on either path, and every write the review process makes (#1216) are minted through `IEventEnvelopeBroker.CreateSystemAsync`, as acts the system performs on its own account (§SEC14.6.1). `CreateElevatedAsync` is not used: none of them is a person's decision.
20. **What the workflow reads, and as whom.** The approval process reads the round's live assignment and the item's score through `IAccessBroker`, never filtered by identity: the flow runs as whoever changed the item, who may see nothing on the round (§APR8.6.2.1, *The security boundary* rule 3). What the review process reads, and as whom, is #1216's, under the same rule: a not-found from a caller-facing read is not a row that does not exist.
21. **Berean's assignment records where its review stands.** `AIReviewerAssignment` carries five tracking fields: `IsAIReviewStarted` and `AIReviewQueuedAt`, set as the review process starts the review; `IsAIReviewCompleted` and `AIReviewCompletedAt`, set as it completes it; and `IsAIReviewCommentsPresent`, whether it filed a comment (I1.5a, I1.6). The review process sets them (#1216). All five start empty — `false`, and null for the two times — and the caller-facing add refuses an assignment that arrives with any of them set, as it refuses the two flags today. Only a data change clears them (rule 9, step 3): a dismissal that is no data change and a withdrawal leave them as they are (I1.5c, I2.D). *(I1.5a, I1.6)*
22. **A round that requires no review is approved as it opens.** Where the resolved `RequireApprovals` is `false`, or the item is a personal association — a reader's own reaction, as a Like is (§DOM4.10) — the approval process approves the round, whatever `AutoApproveIfAllApprovalRequirementsMet` says, and asks no count, no rejection and no comment of it (I2.E, I3.1 steps 4.1 and 4.2): there is no review requirement, and the item leaves the review queue. Berean is never offered on such a round (rule 3), so nobody is asked onto it before it is decided. The administrators' reset re-opens such a round without approving it again, because its `-Submitted` reaches no step 4 (rule 23): it stands `Submitted` until a fact the round re-tests, or a person's next update, approves it (*Risks*). So does a round whose resolved policy stops requiring review while it stands open, because nothing re-tests a round on a change to the approval settings (*Risks*). The one exception is a round Berean was assigned to while the offer still allowed it: before rule 3's terms shipped (`Backend/Clients/AccessClient.BereanReview.md §3`), when the offer was the resolved switch alone, so that a round that never required review could be asked for Berean or assigned it automatically while it stood open; or while the round still required review, before its resolved policy stopped requiring it. Rules 10 and 11 still hold such a round until a person's next add or update, whose step 4 removes Berean from it (rule 9, step 4.3; R9), and before then a bypass, or the withdrawal rule 18 allows, gets past them (I1.5b). *(This replaces §APR8.4 rule 1's and §APR9.7.3 rule 3's approval of such a round only where `AutoApproveIfAllApprovalRequirementsMet = true`.)*
23. **The administrators' reset leaves Berean as it is, and fires nothing of Berean's.** §APR8.6 HR-4's reset re-opens the same content, so it is no data change, and it is no person's add or update (R4). Berean's assignment, its tracking fields, its vote and the item's score stand on the re-opened round as they were (rules 7 and 21; I1.4, I2.D, R5); no Berean is assigned, and no review event is published, so Berean neither reviews nor votes again. The reset's command answers with the item's `-Submitted` under the system identity, which every ear of the Modified flow drops (§ARC16.7.5), so step 4 never runs for it. That guard stays: without it, the flow's evaluation would approve again the round the reset had just re-opened, wherever its policy approves on met conditions. **The reset dismisses the people's active reviews, and Berean's vote stands** (R5): *"Every human reviewer is dismissed. Only Berean remains unchanged."* This narrows §APR8.8 regardless-rule 1 for Berean alone. Berean's vote is built under #1216, and so is the reset's exemption of it, as rule 9 step 1's dismissal of Berean's vote alone is: until then no round holds a vote of Berean's, and the reset's dismissal is unchanged. After the reset, the round is re-tested on the facts that follow, as every round is: the low-score block reads the standing score where Berean is assigned (rule 10), and Berean's standing vote counts as it did (rule 5). *(R4, R5. This rule replaces this design's earlier reading, under which the reset's `-Submitted` reached step 4, and step 4 published the review event so that Berean voted again on its standing score.)*
24. **Only the item's review tier reads its score, its reason and their provenance** (R6, R8). Every read of an approvable item answers its four `IConfidence` fields — `ConfidenceScore`, `ConfidenceReason`, `SourceBatchId` and `ModelVersion` — to the item's review tier, and answers all four as null to every other reader, the anonymous reader of a published post included — not refused, so that their absence tells nobody whether a score exists, as the confidence suggestion answers that tier alone (design PR #1112, its rule 6). The provenance goes with the score because a score always carries it (rule 1), so a set `ModelVersion` beside a null score would tell a reader that a score exists (R8). The tier is the one that rule names. How it is built, on which reads and at which layer, is designed under #1230. **The review process's first write of a score waits for #1230's tasks on `main`** (*What ships together*, step 9): until then no item but an association holds a score, and an association's four fields reach every caller who may read the association, as they do today. `Backend/Models/IApproval.md §1` puts the four fields on every item's contract as designed. *(R6, R8)*

## Layer placement

1. **The decision is the security client's**, as every §APR8.5 condition is (§APR8.6.1 rules 2 and 4): `IAccessClient` evaluates the low-score block, Berean's pending and in-flight blocks, and a round that requires no review, from what `IAccessBroker` gathers — the item's score, which the broker reads off the item for every approvable type, and the round's live Berean assignment with its start and completion. The offer (rule 3) is composed in `IAccessClient.ResolveAIReviewerPolicyAsync`, in the one place the request's gate and the approval process's step 4.2 read it.
2. **The score is each item's own, so each item's foundation writes it**, through its set-confidence operation and that operation's request door, which admit the system identity alone (rule 1). That is §SEC14.7 posture A′'s caller-facing door, not a workflow seam, because the write must reach seven foundations from services that hold none of them: a request address is how the approval workflow already reaches every item (`ApprovalOrchestrationService` publishes `<Entity>-Approving` and holds no item service), and a seam would add a dependency per item type. The gate refuses every context but the system identity, which only this system can mint onto a signed envelope (§SEC14.6 rule 4).
3. **Berean's lifecycle stays in `AIReviewerOrchestrationService`** (§ARC12.5 entry 4): a person's request and the review event it publishes, the withdrawal and its gate, and the status read. It spans `Approval` and `AIReviewerAssignment`, two entity services, and gains `IEventBroker`, to publish, a broker of the kind an orchestration may hold, outside the count (§ARC12.5). Its two subscriptions on `Approval-Added` and `Approval-Modified` leave it, because the approval process assigns Berean itself (item 4).
4. **The round's rules stay in `ApprovalOrchestrationService`** (§ARC12.5.3): the data change's dismissals and clears, step 4's assignment and review event on every add and update, the reset, the re-tests and the blocks' words. It adds no dependency: it clears an item's score through the item's set-confidence door, as it approves through `<Entity>-Approving`, with the `IEventBroker` it holds, which also publishes the review event; it dismisses, clears, assigns and removes Berean through the `IAIReviewerAssignmentWorkflowService` seam it holds; and it reads through the `IAccessBroker` it holds. **The automatic assignment moves here** because the ruling makes it a step of the approval process: after the approval of a round that requires no review, before the evaluation, and as an upsert after a dismissal (I3.1 step 4.3, I4.2), which a gate standing down on any assignment ever made cannot be (§APR8.6.2.1 gate 6). The event then fires once, after it (I5.1). One home keeps that order and that single event.
5. **The review process is #1216's.** The review event's address is `AIReviewerOrchestration-Reviewing`: its subject is its receiver's class name minus `Service`, and the receiver is Berean's lifecycle owner, `AIReviewerOrchestrationService` (§EVN2), as `ContentItemProcessingService` receives `ContentItemProcessing-*`. *(It was named `AIReviewer-Reviewing` until 2026-10-15, against §EVN2; nothing had been built under that name.)* #1216 designs what answers it, and may place the strategies in a service of their own behind it. Both halves of §APR8.6.2's *Explicitly open* question 3 are #1216's. *(This item used to place the classification in a `ContentAnalysisService` behind `ContentAnalysis-Scoring` and `ContentAnalysis-Scored`, with a write-back in `AIReviewerOrchestrationService`. None of it was built, and I3.8 leaves the design to #1216.)*

## Risks

- **Reversible:** every gate, the client's rules, the pages, the orchestration flows, the subscriptions' retirement, and the seed's values.
- **Not reversible:** the seven tables' new columns, and the assignment's three, can be dropped again only by losing every score, start and completion written since. The column rename keeps every value and is reversible by renaming back.
- **The low-score block meets existing scores.** Today `BlockOnZeroApprovalScore` blocks a score of exactly `0` on any association, set by hand, since nothing else has written one. Once rule 10 ships it blocks only on a round Berean is assigned to, so such a score stops blocking on a round Berean is not on, and on a round it is on, every score below `2.50` is held until it is bypassed, since nobody may correct a score once rule 1 ships.
- **An association held by a low score where no bypass is allowed can never be approved.** Under a tier with `BlockOnRejectApprovalScore = true` and `DoNotAllowBypassingSettings = true`, an association scored below the rejection threshold with Berean assigned stays held for good: its score never changes on unchanged content (rule 7), its `-Modified` carries no content and so is no data change (rule 9), nobody may correct a score (rule 1), the bypass is closed (§APR8.6 HR-4 route 3), and its review has started, so Berean cannot be withdrawn (rule 18). What is left is to reject it, or to remove the association and add it again, which starts a new round on a new row with no score.
- **Berean's vote can decide a round.** Where `IsAIAllowedToVote` is on, a score above the approval threshold meets a count of one, and a tier with automatic approval then publishes the item on Berean's vote alone (rule 5, I4.3); a score below the rejection threshold, a null one included, is a rejection that ends the round under `BlockOnReject` (§APR8.7 rule 1). The seed ships the vote off.
- **An automatically requested Berean that never starts holds its round until it is bypassed.** It cannot be withdrawn (rule 18), so where the event is lost, or the review process fails or never answers, the round is held until a bypass, a change to the policy, or a person's request, which publishes the event again (rule 4, I7). Under `DoNotAllowBypassingSettings = true` only the policy change or the request is left.
- **An assignment made before the review event ships never starts.** Every assignment made before rule 4's publishers reach `main` — a person's request or the automatic assignment — never had its event published. Once the gathers ship (*What ships together*, step 4), each round holding one is held by the pending block until a person asks for Berean again, which publishes it (I7), its item changes, or it is bypassed, or — where the policy does not ask for Berean automatically — Berean is withdrawn.
- **The review process will hear the event more than once for one assignment.** Step 4 publishes it on every update of a `Submitted` round while Berean is assigned, and a person's request does whenever Berean stands assigned (rule 4). What a second event does is #1216's (rule 17).
- **Withdrawing Berean lifts the pending block**, only before its review starts and only where the policy does not ask for Berean automatically (rule 18). A6 rules that a null score does not block without Berean, and a round can then be decided before Berean has looked. The withdrawal is on the row.
- **A round that requires no review is approved whatever its comments** (rule 22). No comment can arise on it before it is first decided, because it is approved as it opens; a round that was open before rule 22 shipped, one the administrators' reset re-opened, or one whose resolved policy stopped requiring review while it stood open, is approved at its next evaluation whatever comments it then holds, unless Berean holds it.
- **A round whose policy stops requiring review while it stands open waits for its next re-test.** Nothing re-tests a round on a change to the approval settings: no subscriber that re-tests a round binds an `ApprovalSetting` fact (§EVN18; `EventSubscriptionRegistration.cs` binds the setting's request addresses alone). So a round that stands `Submitted` when an administrator's change to the settings leaves it resolving `RequireApprovals = false` — the tier's switch turned off, or a tier added or removed — stays in the review queue I2.E has it leave until a fact the round re-tests arrives, or a person's next update runs step 4, and either approves it (rule 22), whatever comments it holds. Until then the offer's terms refuse a person's request for Berean on it (rule 3), a publisher's approve asks it no count, rejection or comment (`Backend/Clients/AccessClient.BereanReview.md §8`), and a Berean assigned while it still required review holds it (rules 10, 11 and 22), until a person's next update removes Berean (rule 9, step 4.3; R9).
- **A round that stops offering Berean loses Berean's hold at a person's next add or update** (R9). Step 4 removes Berean from it, whatever Berean's review has reached, so the pending and in-flight blocks lift, and so does the low-score block: a low score, a missing one included, stops holding the round, and a review in flight no longer holds it, so the round can be decided on its people's reviews before that review completes (rule 9, step 4.3). The owner ruled the removal for that round, because Berean is no longer offered there. It is reversible: once the round offers Berean again, a person may ask for it, or the policy assign it at the next add or update, and the score the removed review left stands on the item (rule 7).
- **A reset round that requires no review is approved again at its next re-test.** The reset re-opens it at `Submitted` (§APR8.6 HR-4), and its `-Submitted` reaches no step 4 (rule 23), so it stands in the review queue I2.E has it leave until a fact the round re-tests arrives — a review, a comment or an assignment of Berean's — or a person's next update runs step 4. Either approves it, whatever `AutoApproveIfAllApprovalRequirementsMet` says (rule 22), undoing the reset's override, as Berean's standing vote can (below). The reset asks nothing of whether the item is a personal association (`ApprovalOrchestrationService.Resets.cs`), so a reader's reaction whose round an administrator resets is one such round, and waits on review until then.
- **An automatic assignment that fails leaves the round unheld.** Where step 4.2's add fails — a dependency failure, not the collision `Backend/Orchestrations/ApprovalOrchestrationService.BereanReview.md §7` rule 5 contains — the flow faults before its own evaluation, so that evaluation never approves the round without Berean. Nothing else holds it: no condition reads the automatic request, so the round's next re-test evaluates it without Berean, and a round whose conditions are then met is decided without Berean's review. What brings Berean back is a person's next update, which runs step 4 again, or a person's request. The failure is in the error log. The owner ruled that it stays so: nothing holds the round until Berean is added (R7).
- **A reset round can be approved again on Berean's standing vote.** The reset leaves Berean's vote (R5, rule 23), and the vote counts as a person's (rule 5), so on a tier that needs one approval, with automatic approval on, the re-opened round is approved again at its next re-test wherever no other condition holds it — undoing the override the reset made. The owner ruled the vote to stand because, with no data change, it would be the same vote on the same score (R5). Only a data change dismisses it (rule 9). The seed ships the vote off.
- **Watch for** the gathers for Berean's blocks being merged before the review process (*What ships together*, step 4).
