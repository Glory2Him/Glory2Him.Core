# Berean's review
Epic: [INTENT.md](../../INTENT.md)
Inherits: §APR7.8, §APR8.2, §APR8.4, §APR8.5, §APR8.6 HR-4, §APR8.6.1, §APR8.6.2, §APR8.6.2.1, §APR9.2 rule 4, §APR9.7.1 rules 2 and 5, §APR9.7.4, §APR13.2, §APR13.4, §ARC12.1, §ARC12.5, §ARC12.5.3, §ARC16.7.1, §DOM4.9, §EVN2, §EVN3, §EVN18, §EVN19, §SEC14.6, §SEC14.6.1, §SEC14.7 postures A and A′, §UI20.5.1, LiveUpdates.md rule 3, PostModeration.md rule 13
Mockups: none. The indicator is ruling 1's own description, and the two approval-setting screens keep their layout.
Design task: #1117

Berean is the reviewer a moderator can ask onto a round, or that a policy asks for them. It casts no vote. Asking it starts the confidence process, which records a confidence score and a reason on the item under review, and Berean's row on the round shows only whether that review is pending or complete. A low score can hold the round's final approval shut until somebody bypasses it, and while Berean is assigned and has not answered, the round waits for it.

## Problem

Berean was designed to vote: to file an `ApprovalReview` decided from a confidence score against two thresholds (§APR8.6.2 rules 1–3). A publisher or administrator could set or correct that score by hand (§APR9.7.1 rule 5), only an `Association` carried one (§APR8.6.2, *`ContentItem` is deliberately not scored*), and the only block on it was a score of exactly zero (`BlockOnZeroApprovalScore`, §APR8.5 rule 8). None of the voting was built, and nothing ever completed Berean's review: its assignment's two flags had no writer (§APR8.6.2, *Trigger event — NOT built*). The owner ruled on 2026-10-13 that Berean does not vote, that no person sets a score, that every approvable item is scored, and that a low score, or a score Berean still owes, holds the round.

## The rulings

The owner ruled on 2026-10-13, in their own words. Rulings 1–3 are #1117's, and the answers A1–A7 are to #1117's open questions 1–7.

1. *"non-system users will NOT be able to set it [the confidence score/reason] by hand. They cast their vote based on their own confidence (or by factoring in what Berean answered). Berean is assigned as an AI reviewer, but it can't actually vote itself. With it being requested as a reviewer, it triggers the confidence process which then gives its confidence score and reason. The only outcome from the Berean reviewer is an indicator status: Requested / busy (isAIReviewCompleted false): a yellow filled dot (bi-circle-fill text-warning) with the tooltip 'Berean's review is pending'. It replaces the 'Requested' badge a human reviewer would get. Completed (isAIReviewCompleted true): two glyphs on the same line. A recycle icon (bi-arrow-repeat) is a button with the tooltip 'Re-request Berean review'; it raises onAIReviewerRequested. A chat-bubble icon (bi-chat-dots) is blue with 'Berean left review comments' if there are comments, and muted grey with 'Berean left no comments' if there aren't."* The recycle button is withdrawn by A7.
2. *"If Berean is enabled, it will trigger the confidence process the moment something comes in that requires review (excluding things that are auto approved i.e. Likes). If Berean is NOT enabled, the confidence process will not start and therefore the values will remain NULL."*
3. *"The confidence process has its own thresholds. The shipped Berean thresholds are 2.50 for rejection and 7.50 for approval. They sit on the 0.00–10.00. … If Berean is enabled, then these values will weigh into the voting, i.e. a low score may prevent final approval UNLESS bypass is used."*
- **A1 — where the thresholds live:** *"This already lives on ApprovalSetting"*.
- **A2 — what *enabled* is:** *"ApprovalSetting.IsAIReviewerOffered = true"*. **Which rounds are skipped:** *"ApprovalSetting.RequireApprovals = false OR ApprovalSetting.IsPersonal = true. Both these will not require a review round so Berean's confidence process should not be started on them."*
- **A3 — the block:** *"Lets rename `ApprovalSetting.BlockOnZeroApprovalScore` to `ApprovalSetting.BlockOnRejectApprovalScore`. If `ApprovalSetting.BlockOnRejectApprovalScore` is boolean field has a true value, then the rules must block approvals. The only way to get past this is to use the bypass feature. If `ApprovalSetting.BlockOnRejectApprovalScore` is false, then this advisory is NOT enforced. The gate will compute this value as a boolean value based on the applicable ApprovalSetting -> `BlockOnBelowBereanRejectionScore` = Berean confidence score <= ApprovalSetting.AIApprovalConfidenceRejectionThreshold"*
- **A4 — what is scored:** *"Anything that is subject to approval will get the option of adding Berean as a reviewer. If ApprovalSetting.IsAIReviewerOffered = true, then Berean can be added as a reviewer either manually or via ApprovalSetting.IsAIReviewerAutomaticallyRequested = true. This will trigger the confidence process that will then record a confidence score and reason against the approval. The confidence score and reason will always be there BUT what is scored will depend on the type of approval. … We still need to build the confidence process, but the outcome is uniform and generic for all. If the confidence score is <= than what is recorded on ApprovalSetting.AIApprovalConfidenceRejectionThreshold then the gate MUST block the approval if ApprovalSetting.BlockOnRejectApprovalScore = true, otherwise the score and reason will just be visible warning on the UI."* **Corrected the same day:** *"It is recorded against the entity that implements IApproval since IApproval implements IConfidence … Association must not implement IConfidence again since it is getting it via IApproval"*, with the target declaration `public interface IApproval : IConfidence { … }`, its existing members unchanged. The owner's examples of what each type is judged on — a content item's theme, a tag's language and spelling, a Bible reference's existence and its quoted text, an association's pairing — are examples, not rules: what is judged is the classification's (*Out of scope*).
- **A5 — comments:** *"That will depend on the confidence process. I would think in general the confidence process will only do the score and reason for the score. But we might do the confidence process and decide we want to also submit comment or question than may need resolution i.e. submit a question that will block the review round …"*
- **A6 — a null score:** *"If Berean is assigned as a reviewer, then a null score MUST block the approval to allow the confidence process to complete. If Berean is not assigned as a reviewer, then the null score MUST not block the review round as it simply means Berean was not required."*
- **A7 — re-runs:** *"A score on unchanged content never changes. From a UI perspective, you cannot request a re-review. The UI will only show Requested and then the status of where the confidence process / Berean are. If a review round is cleared as dismissed due to a change, then Berean can be manually added which will then trigger a re-review OR when the round is cleared as dismissed but Appsetting.IsAIReviewerAutomaticallyRequested = true, then the approval MUST automatically add Berean for the new round (verify this happens today). Following this, users cannot abuse the re-review to force a new score or stack up costs for AI reviews."*

## Business rules

1. **No person sets a confidence score or reason.** The four `IConfidence` fields — `ConfidenceScore`, `ConfidenceReason`, `SourceBatchId`, `ModelVersion` — are written only by the system identity, through each entity's set-confidence operation (§APR9.7.1 rule 5). Every other caller is refused there, `Publishers` and `Administrators` included, and an item's add and general modify never accept them (§APR9.7.1 rule 2). *(ruling 1)*
2. **Every approvable entity carries a score and a reason.** `IApproval` extends `IConfidence`, so `ContentItem`, `Link`, `Tag`, `Reaction`, `Comment`, `BibleReference`, `Attachment` and `Association` all carry the four fields, and `Association` no longer declares `IConfidence` itself (§APR9.7.1 rule 5). The score sits on the item, not on its round: a round is the item's approval, and what the score judges is the item. `Attachment` has no round of its own (§APR7.5.1 rule 5), so its fields stay null. *(A4, as corrected)*
3. **Berean is offered where the round's resolved policy offers it and requires review.** It is offered where the resolved `IsAIReviewerOffered` is `true`, `RequireApprovals` is `true` and the resolved row is not keyed `IsPersonal = true` — on every approvable entity type that has a round (rule 2). Everywhere else it is not offered, cannot be asked, is never assigned automatically, and nothing it does is performed (§APR8.2, the `IsAIReviewerOffered` row). A Like's round is skipped on both counts: the seeded personal tier has `RequireApprovals = false` and is keyed `IsPersonal = true`. *(A2)*
4. **Assigning Berean starts the confidence process, and nothing else does.** Berean is assigned by a person's request (`POST`, §APR8.6.2, *Assignment*) or automatically where the resolved policy offers it and `IsAIReviewerAutomaticallyRequested` is `true` (§APR8.6.2.1), and each assignment's arrival starts one run (rule 6). There is no re-request (rule 8), no return of an assignment to pending (rule 9), no run over historical rows (§APR13.4 rule 4 is retired), and no start off the round's own facts. A round that entered review before its tier offered Berean has none until somebody asks. *(ruling 1, A4, A7)*
5. **Berean casts no vote.** It files no `ApprovalReview`, so nothing it does counts toward `RequiredNumberOfApprovals` or triggers `BlockOnReject`. `IsAIAllowedToVote` and `CK_ApprovalSetting_AIVoteRequiresAIReviewer` are retired (*Storage and migration*). *(ruling 1)*
6. **A run records a score and a reason on the item, and may file comments.** A run writes the item's four `IConfidence` fields as one unit (§APR9.7.1 rule 5) and may file `ApprovalComment`s on its round: a remark, created settled, or a question, created outstanding, which holds the round shut while `RequireReviewCommentResolutionBeforeApprovals` is on (§APR7.8, §APR8.5 rule 7). Which comments a run files, if any, is the classification's (*Out of scope*). A question Berean files is settled on its behalf by the publisher tier (§APR8.5 rule 7, route 2), since Berean is not a person who can settle it. *(A5)*
7. **A score on unchanged content never changes.** Set-confidence writes a score only onto an item that has none, and leaves a stored score as it is. Only rule 9's clearing removes one. So withdrawing Berean and asking again on unchanged content runs nothing: the new assignment completes at once, reporting no comments, because it filed none. *(A7)*
8. **Berean's row shows where its review stands, and offers nothing else.** While the assignment is pending (`IsAIReviewCompleted` is `false`), a yellow filled dot (`bi-circle-fill text-warning`) with the tooltip *"Berean's review is pending"* stands where a person's *Requested* badge would. Once it is complete, a chat-bubble (`bi-chat-dots`) stands there: blue, with *"Berean left review comments"*, where `IsAIReviewCommentsPresent` is `true`, and muted grey, with *"Berean left no comments"*, where it is `false`. There is no re-request control (`UI/Components/ReviewPanel.md` rule 2.45). *(ruling 1, A7)*
9. **A content change that dismisses the round clears Berean's review, and only that.** Where the Modified flow dismisses a round's reviews because the item's content changed under `RequireReapprovalOnChange = true` (§APR8.8 rule 1, §APR9.7.4), it also clears the item's four `IConfidence` fields and dismisses the assignment that was Berean's live one when the flow began, both before it evaluates the round. Then, where the resolved policy offers Berean and asks for it automatically (rules 3 and 4), and no live assignment stands on the round, it assigns Berean afresh for the new round, whatever happened to Berean on the content that has gone, a withdrawal included. Where it does not, Berean stays off until a person asks, and that request starts a fresh run, the score being null. **An assignment the round gains during the flow is the new round's, and is neither dismissed nor doubled.** The one that can arise is the automatic assignment hearing the `Approval-Modified` of a `Draft` round the flow moves to `Submitted` (§APR9.2 rule 3, §APR8.6.2.1), which runs inside that move's publish, because delivery is synchronous (§EVN11): so a submission through the general modify starts one run, not two. Nothing else clears a score or dismisses Berean: not a `-Submitted` from `Draft`, which changes no content; not an association's `-Modified`, which can carry none (§APR7.5.1 rule 4); not §APR8.6 HR-4's reset, which re-opens the same content; not a changed reaction, whose round never offers Berean (rule 3); and not the dismissal of an amender's own review alone (§APR8.6.3 rule 7). Under `RequireReapprovalOnChange = false` nothing is dismissed and the score stands, as the reviews do (§APR8.6 residual 1). Whether a modify that changes no content field — an echo of the stored row, which still publishes `-Modified` and, under `RequireReapprovalOnChange = true`, dismisses the reviews today (§APR9.7.4) — counts as a content change here is open (*Open questions* 2). *(A7)*

   **What happens today, checked on `main` at a3943d8a, as A7 asked.** Both paths that dismiss — the Modified flow under `RequireReapprovalOnChange = true` and HR-4's reset — return a live, completed assignment to pending, through `IAIReviewerAssignmentWorkflowService.ReturnStaleAIReviewerAssignmentToPendingAsync` (`ApprovalOrchestrationService.Flows.cs:192-197`, `ApprovalOrchestrationService.AIReviewer.cs:98-124`), whatever `IsAIReviewerAutomaticallyRequested` resolves to. Neither adds Berean where it was never assigned or was withdrawn: the reset's helper finds only a live, completed row (`AccessBroker.FindResettableAIReviewerAssignmentIdAsync`), and the automatic assignment hears `Approval-Added` and `-Modified` alone, whose gate 6 stands down wherever any assignment row exists (§APR8.6.2.1). Because nothing completes an assignment today, no assignment is ever completed, so in practice neither path changes anything. Rule 9 replaces both behaviours.
10. **The low-score block.** `BlockOnZeroApprovalScore` is renamed `BlockOnRejectApprovalScore`. Where it resolves `true`, an item whose score is at or below the round's resolved `AIApprovalConfidenceRejectionThreshold` cannot meet the §APR8.5 conditions, on the automatic approval and the manual approve alike, and only a bypass gets past it (§APR8.6 HR-4 route 3). Where it resolves `false`, the score blocks nothing and is a warning a moderator reads. The block reads the stored score whatever rule 3's switches say, so a score left from before a tier stopped offering Berean still counts. A null score is not a low score. *(A3, A4)*
11. **The pending block.** While Berean is assigned to a round — it holds a live assignment — and either the item's score is null or Berean's review has not completed, the round cannot meet the §APR8.5 conditions, whatever `BlockOnRejectApprovalScore` says, so the confidence process can complete before anyone decides. A completed review always leaves a score, because the write-back refuses an answer that carries none and writes the score before the completion (rule 16), so the two halves are A6's null score held until the process has finished, a question it files included. A bypass gets past it, and so does withdrawing Berean, after which a null score blocks nothing. Where Berean is not assigned, a null score blocks nothing. *(A6)*
12. **The thresholds stay on the approval-setting tiers.** `AIApprovalConfidenceRejectionThreshold` and `AIApprovalConfidenceApprovalThreshold` stay per-tier columns, resolved through §APR8.4, on the 0.00–10.00 `decimal(4,2)` scale, with their three check constraints. The seed ships `2.50` and `7.50`. They are read whatever `IsAIReviewerOffered` resolves to: the rejection threshold by rule 10, and the pair by the confidence suggestion designed under #863 (design PR #1112, not yet on `main`), whose band relies on their order. *(A1, ruling 3)*
13. **Where no settings row resolves.** The fail-closed default (§APR8.4 rule 2) holds `BlockOnRejectApprovalScore = true` with both thresholds at `0.00`, so only a score of exactly `0.00` blocks there, as the zero block did, and `IsAIReviewerOffered = false`, so Berean is never assigned and rule 11 never arises.
14. **What reaches the moderation pages.** Asking Berean and withdrawing it each move the verdict (rule 11), so each moderation page refreshes the verdict as well as Berean's status after either. What a run writes later reaches an open page through the round's 15-second refresh, which re-reads the item, Berean's status, the thread and the verdict (`UI/Pages/ContentItemModerationDetailPage.md` rule 2.12, `UI/Pages/AssociationModerationDetailPage.md` rule 2.18); nothing is pushed (`LiveUpdates.md` rules 3 and 7). The association page shows the score and reason in its confidence block (`PostModeration.md` rule 13).
15. **The approval-setting screens.** The detail page at `/Admin/ApprovalSettings/{approvalSettingId}` drops *"Allow Berean to additionally cast a vote"*, leaves both threshold inputs editable whatever the switches say, labels the block switch *"A low Berean confidence score blocks approval"* (it read *"A zero confidence score blocks approval"*), and explains the inputs as *"A Berean confidence score at or below this blocks approval while “A low Berean confidence score blocks approval” is on."* and *"A Berean confidence score above this suggests an approval to the moderator."*, and the order as *"Approve above must not be below Reject below."* The list at `/Admin/ApprovalSettings` drops its *AI vote* pill and renames *Blocks on zero score* to *Blocks on low score*. **This rule stands in for the two screens' user stories.** Neither page has a page document, because `UI.md` §UI20.5.1 asks one only of a page that renders a documented presentation component, and neither renders one. Nor can either have a user story document: `design.md`'s level folders give a page none, since in this repository a page's design is its page document (`design.md`, *Level folders*: `UI/` has no `Pages` folder). So this rule is the whole of the two screens' design, and the tasks that build them (#1143, #1144) name it on their *User story* line, in a user story's place.
16. **A run that fails, stops part-way, answers without a score or never answers.** A run's answer is written in this order: the item's score, then Berean's comments, then the assignment's completion (`Backend/Orchestrations/AIReviewerOrchestrationService.BereanReview.md §3`). An answer that is not a score — any of the four fields absent, or one outside set-confidence's shape (`Backend/Foundations/TagService.BereanReview.md §3` rule 3) — writes nothing and completes nothing, so a completed review always leaves a score. A write that fails ends the write-back there, and nothing in this host delivers a failed delivery again (§EVN23 rule 6): what it wrote stays, and the rest is never written. Until the completion lands the round stays held (rule 11), so a run that fails, stops part-way, answers without a score or never answers leaves the round held, and never lets it through. The person's way out is to withdraw Berean, which lifts rule 11's block (rule 18). Then they ask again: where the score landed, the new assignment completes at once (rule 7), and where it did not, a fresh run starts. Each failure is logged, and nothing is silently dropped.
17. **A run in flight.** A run's writes land only while the assignment that started it is live and not yet completed. A run whose assignment was withdrawn, dismissed by rule 9, or already completed writes nothing. Withdrawing and asking again before the first run answers starts a second run, and discards the first's result. That spends a second classification: an accepted cost of a person's two acts, recorded on the two assignment rows (*Risks*).
18. **Withdrawing Berean keeps the score.** The score judges the item, not the assignment, so it stays where it is. A withdrawal lifts rule 11's block, and that is all it changes.
19. **Every write a run makes is the system's own.** The score, the comments and the completion are minted through `IEventEnvelopeBroker.CreateSystemAsync`, as an act the system performs on its own account (§SEC14.6.1), on a person's request as on the automatic start. `CreateElevatedAsync` is not used: the score is not a person's decision.
20. **What a run reads, and as whom.** The start reads the round through the approval workflow seam and whether its item is already scored through `IAccessBroker`, neither filtered by identity. The confidence process reads the item — and, for an association, its two endpoints — under the system identity, through reads no identity filters, never a caller-facing read. A not-found from a caller-facing read is not a row that does not exist (§APR8.6.2.1, *The security boundary* rule 3). An item that reads back absent or taken down ends the run with nothing written, under rule 16.

## Layer placement

1. **The decision is the security client's**, as every §APR8.5 condition is (§APR8.6.1 rules 2 and 4): `IAccessClient` evaluates both blocks from what `IAccessBroker` gathers — the item's score, which the broker reads off the item for every approvable type, and whether a live Berean assignment stands on the round. The offer (rule 3) is composed in `IAccessClient.ResolveAIReviewerPolicyAsync`, in the one place gate 4 and the request's gate already read it (§APR8.6.2.1 gate 4).
2. **The score is each item's own, so each item's foundation writes it**, through its set-confidence operation and that operation's request door, which admit the system identity alone (rule 1). That is §SEC14.7 posture A′'s caller-facing door, not a workflow seam, because the write must reach seven foundations from services that hold none of them: a request address is how the approval workflow already reaches every item (`ApprovalOrchestrationService` publishes `<Entity>-Approving` and holds no item service), and a seam would add a dependency per item type. The gate refuses every context but the system identity, which only this system can mint onto a signed envelope (§SEC14.6 rule 4).
3. **Berean's lifecycle stays in `AIReviewerOrchestrationService`** (§ARC12.5 entry 4): the request, the start and the write-back. It spans `Approval`, `AIReviewerAssignment` and `ApprovalComment` — three entity services, each a foundation, within two-to-three — and reaches the item by request address alone, so no item service is added. It gains `IEventBroker`, to publish, a broker of the kind an orchestration may hold, outside the count (§ARC12.5).
4. **The round's rules stay in `ApprovalOrchestrationService`** (§ARC12.5.3): the content change's clearing and dismissal, the reset, the re-tests and the block's words. It adds no dependency: it clears the item's score through the item's set-confidence door, as it approves through `<Entity>-Approving`, and it dismisses and re-adds Berean through the `IAIReviewerAssignmentWorkflowService` seam it already holds.
5. **The classification call lives in the confidence process's own service, behind a request address, not inline in any handler** (§APR8.6.2 open question 3, its first half). The start publishes `ContentAnalysis-Scoring`, and the process answers with `ContentAnalysis-Scored`. Its service, `ContentAnalysisService` (§ARC12.1 item 8, §APR13.1), is not designed here. What backs the call is still open (§APR8.6.2 open question 3, its second half), and so is what each type is judged on. So is how the service reaches each item type: a run reads one item, or an association and its two endpoints, which is three entity types at most (§ARC12.1 rule 2). But a single service answering every type would hold a service per type, and would have to keep within two-to-three by splitting per type, or bring a deviation to the owner. That choice is made with what backs the call.

| The write-back (rule 16) | `Approval` (the round, read for its item and its status), `ApprovalComment`, `AIReviewerAssignment`, and the item (by request address) — four | `AIReviewerOrchestrationService` |
| The content change (rule 9) | `Approval` (the round it evaluates), `ApprovalReview` (the reviews it dismisses), `AIReviewerAssignment`, and the item (by request address) — four | `ApprovalOrchestrationService` |
| The blocks (rules 10–11) | gathered by `IAccessBroker`, decided by `IAccessClient` | client and broker |

**Two flows span four entity types, and the fourth is reached by events.** In the write-back and in the content change, three entity types are reached through entity services and the item only through its set-confidence request address (*Layer placement* items 2 and 4). Four types through four services would break two-to-three, and that is why the item is reached by event: no item service is added to either orchestration, and neither holds more than three entity services. `AIReviewerOrchestrationService` goes from two entity services to three (`IApprovalWorkflowService`, the `AIReviewerAssignment` pair — counted once, §ARC16.7.1 finding 2 — and the new `IApprovalCommentWorkflowService`). `ApprovalOrchestrationService` keeps its three (`IApprovalWorkflowService`, `IApprovalReviewWorkflowService`, `IAIReviewerAssignmentWorkflowService`).

## Events

| Direction | Address | Who | Why |
| --- | --- | --- | --- |
| Consumed | `AIReviewerAssignment-Added` | `AIReviewerOrchestrationService` | the start (rule 4) |
| Published (request) | `ContentAnalysis-Scoring` | `AIReviewerOrchestrationService` | asks the confidence process for a run |
| Consumed | `ContentAnalysis-Scored` | `AIReviewerOrchestrationService` | the write-back (rule 16) |
| Published (request) | `<Entity>-SettingConfidence` | `AIReviewerOrchestrationService`, `ApprovalOrchestrationService` | writes, or clears, the item's score |
| Consumed (request) | `ContentItem-SettingConfidence`, `Link-SettingConfidence`, `Tag-SettingConfidence`, `Reaction-SettingConfidence`, `Comment-SettingConfidence`, `BibleReference-SettingConfidence` — new; `Association-SettingConfidence` — existing | each item's foundation | set-confidence's door |
| Published (fact) | `<Entity>-ConfidenceSet`, one per item type | each item's foundation | no subscriber, as today |
| Consumed | `AIReviewerAssignment-Added`, `-Modified`, `-Removed` | `ApprovalOrchestrationService` | re-test the round, as every fact of a record that can move a predicate is re-tested (§EVN18(a)): the completion and the withdrawal lift rule 11's block, and the add only holds the round |
| Retired (request) | `AIReviewerAssignment-Modifying` | — | the caller-facing modify has no caller (`Backend/Foundations/AIReviewerAssignmentService.md §3`) |

**Termination.** The start's request is answered by one fact, and the write-back publishes `<Entity>-ConfidenceSet`, `ApprovalComment-Added` and `AIReviewerAssignment-Modified`. The last two re-test the round, and a re-test that decides publishes the item's `-Approved` or `-Rejected` and `Approval-Modified`. `Approval-Modified` reaches the automatic assignment, whose gate 3 refuses a decided round and whose gate 6 refuses a round with an assignment, so the chain ends there (§EVN18(e)). Nothing hears `-ConfidenceSet`, so a score's write starts nothing.

**§EVN18(e)'s boundary moves, and is restated rather than departed from.** Assigning Berean now moves a §APR8.5 predicate — rule 11 — but only toward a block, and a block decides nothing. What lifts it — the completion and the withdrawal — arrives on an `AIReviewerAssignment` address that the re-test hears. So the automatic assignment's binding of `Approval-Added` and `-Modified` meets the restated condition 1: it reads no predicate and moves none toward an approval (§EVN3, §EVN18(e)). §ARC12.5.3's test is restated on the same footing: the round owns the rule and the re-test; the writes that feed them stay where they are, as a review's add stays on `ApprovalReviewService`.

## Storage and migration

1. **The confidence columns on seven tables.** `ContentItems`, `Links`, `Tags`, `Reactions`, `Comments`, `BibleReferences` and `Attachments` each gain `ConfidenceScore decimal(4,2) NULL`, `ConfidenceReason nvarchar(500) NULL`, `SourceBatchId uniqueidentifier NULL` and `ModelVersion nvarchar(128) NULL`, with a check constraint holding the score `BETWEEN 0 AND 10`, as `Associations` already has. Each `ADD` is nullable with no default, so existing rows read null and nothing is updated: one batch, nothing to `EXEC`. No index — nothing filters on them (`Backend/Models/IApproval.md §2`).
2. **The rename.** `ApprovalSettings.BlockOnZeroApprovalScore` becomes `BlockOnRejectApprovalScore`, keeping every row's value, through one column rename (`Backend/Models/ApprovalSetting.md §2`). The seed's constant, `true` on the house policy and `false` on the personal-association row, keeps its values under the new name, and so does its drift comparison.
3. **The vote.** `ApprovalSettings.IsAIAllowedToVote` and `CK_ApprovalSetting_AIVoteRequiresAIReviewer` are dropped, and so are the seed constant and its drift entry (`Backend/Models/ApprovalSetting.md §3`).
4. **The thresholds stay**, with `CK_ApprovalSetting_AIRejectionThresholdRange`, `CK_ApprovalSetting_AIApprovalThresholdRange` and `CK_ApprovalSetting_AIThresholdOrder` and their seed constants (rule 12). Their comments change: the order exists for the suggestion's band (rule 12), not for two verdicts.
5. **No seed consequence beyond these.** No `ContentType` member and no role is added, so §ARC12.5.1's role seed is untouched.

## What ships together, and in what order

Every merge to `main` deploys, and the app migrates as it starts (§APR7.4 item 6, *What must ship together*). No stage below needs a pull request that closes more than one task.

1. **The rename** reaches `main` in four steps, so that no deployment leaves the React app and the server naming the field differently, and none leaves the model and the schema apart. The React model first reads either name and sends both (`UI/Models/ApprovalSetting.md §1`). The ASP.NET Core model binder ignores a JSON member it does not know, so the deployed server keeps binding the old name. Then the server's property is renamed, still mapped to the old column (`Backend/Models/ApprovalSetting.md §1`), and binds the new one. Then the column is renamed (§2). And last, the React model drops the old name (`UI/Models/ApprovalSetting.md §2`).
2. **The vote's column** is dropped only once nothing reads it: both pages, the React model, the security client's policy and the broker's mapping first, then the drop (`Backend/Models/ApprovalSetting.md §3`).
3. **The confidence columns** are mapped only once every add and modify of the six foundations refuses the fields (`Backend/Models/IApproval.md §2`): mapped first, a caller's score would be stored on any path not yet refusing it. Until then the model carries them unmapped (§1). If §APR7.4 item 6's stage 2, which adds `ApprovalId` to `IApproval` and to five of the same tables in one pull request (D1), reaches `main` first, this migration is generated after it, and the other way round. Neither needs the other.
4. **The pending block's gathers wait for the confidence process** (`Backend/Brokers/AccessBroker.BereanReview.md §4–§6`). Merged before anything can answer, they would hold shut every round Berean is assigned to, until somebody withdrew it. The client's rule ships first and blocks nothing while the broker hands it `false` (`Backend/Clients/AccessClient.BereanReview.md §5`). **And the confidence process does not ship before the seven tables' columns are on `main`** (`Backend/Models/IApproval.md §2`): a score written to an item with no column is stored nowhere, so its completed review would leave no score, and once the gathers ship that would hold the round. What the gathers do to an assignment made before the start existed is under *Risks*.
5. **The six items' own writes come before the columns.** Their refusals on add and modify (`Backend/Foundations/<Entity>Service.BereanReview.md §1–§2`), their set-confidence (§3) and their transitions' stored score (§5) each build on the model (`Backend/Models/IApproval.md §1`), and each door (§4) on its set-confidence. Until the columns are mapped each runs and stores nothing, as the amender record's writes ran before its column (§APR8.6.3 rule 10 step 2): the model carries the four properties unmapped, so a caller's value on those items is never stored, and set-confidence's write lands on properties storage ignores. The columns wait for the twelve refusals on `main`, in the order step 3 gives. The content-change flow and the write-back publish to the six doors (`Backend/Orchestrations/ApprovalOrchestrationService.BereanReview.md §2`, `Backend/Orchestrations/AIReviewerOrchestrationService.BereanReview.md §3`), so both build on all six. Before the columns no item but an association holds a score, and the content-change flow clears a score only where one stands, so it sends the six none.

## Risks

- **Reversible:** every gate, the client's rules, the pages, the orchestration flows, and the seed's values.
- **Not reversible:** the vote's drop (`Backend/Models/ApprovalSetting.md §3`) — once the column is dropped, every row's `IsAIAllowedToVote` is gone, though nothing has ever acted on it (§APR8.6.2 rules 1–3 were never built). The column rename keeps every value and is reversible by renaming back. The seven tables' new columns can be dropped again only by losing every score written since.
- **The low-score block meets existing scores.** `BlockOnZeroApprovalScore` is `true` on the seeded house policy, so once rule 10 ships, every association scored at or below `2.50` — scores a publisher set by hand, since nothing else has written one — is held until it is bypassed. Such a score cannot be corrected once rule 1 ships, so the moderator's way past it is the bypass, where the tier allows one.
- **An association held by a low score where no bypass is allowed can never be approved.** Under a tier with `BlockOnRejectApprovalScore = true` and `DoNotAllowBypassingSettings = true`, an association scored at or below the rejection threshold stays held for good: its score never changes on unchanged content (rule 7), its `-Modified` carries no content and so never clears it (rule 9), nobody may correct a score (rule 1), and the bypass is closed (§APR8.6 HR-4 route 3). What is left is to reject it, or to remove the association and add it again, which starts a new round on a new row with no score.
- **A second run's cost.** Withdrawing Berean and asking again while a run is in flight spends a second classification (rule 17). The assignment rows record who did it: the withdrawal's `DeletedBy` and the new row's `CreatedBy`.
- **Withdrawing Berean lifts the pending block.** Anyone in the requesting tier may withdraw it (§APR8.6.2, *Assignment*), so a round can be decided before Berean answers by withdrawing it first. A6 rules that a null score does not block without Berean. The withdrawal is on the row, and the score, when a later request writes it, still counts (rule 10).
- **A write-back that fails part-way holds the round until a person acts.** Nothing in this host delivers a failed delivery again (§EVN23 rule 6), so a write-back that faults after the score, or after one of Berean's comments, leaves what it wrote and never writes the rest: the assignment stays pending, and the round held, until a person withdraws Berean (rule 16, `Backend/Orchestrations/AIReviewerOrchestrationService.BereanReview.md §3` rule 6). Asked again, the new assignment completes at once where the score landed, reporting no comments, though the comments filed before the fault stand on the round; where the score did not land, a fresh run starts, and may file its comments a second time. A question filed twice is settled twice. The round is never let through early.
- **A start heard twice.** Nothing in this host delivers a fact again, but were an `AIReviewerAssignment-Added` heard twice while its run is in flight, it would ask for a second run, whose answer is discarded. That would spend a second classification.
- **An assignment made before the start ships never gets a run.** Every assignment made before `Backend/Orchestrations/AIReviewerOrchestrationService.BereanReview.md §2` reaches `main` — a person's request or the automatic assignment — has had its `AIReviewerAssignment-Added` heard by nothing, and stays pending. Once the pending block's gathers ship (*What ships together*, step 4), each round holding one is held until a person withdraws Berean and asks again, which starts a run.
- **Watch for** the pending block's gathers being merged before the confidence process answers (*What ships together*, step 4).

## Open questions

The owner answered #1117's seven on 2026-10-13, and corrected A4 the same day. Three questions those answers leave. No task depends on the first; one task depends on each of the other two, and waits for its answer.

1. **Who may read an item's confidence score and reason.** Once the seven items carry the fields (`Backend/Models/IApproval.md §1`), they travel on every read of the item, as an association's already do, to every caller who may read the item, a published post's anonymous reader included. Nothing withholds them today, and this design adds and removes no reader. The confidence suggestion answers only the item's review tier (design PR #1112, its rule 6), and the moderation pages are the review tier's. Whether every other reader is to be refused the two fields is the owner's to rule. Until a score is written — which waits for the confidence process — every read carries null.
2. **Whether a re-save that changes no content is a content change for Berean.** A general modify that changes no content field — an echo of the stored row — still publishes `-Modified` (`TagService.DoModifyTagAsync`, as every foundation's modify does), and under `RequireReapprovalOnChange = true` the Modified flow dismisses the round's reviews on it today: §APR9.7.4 holds every `-Modified` to be a content change, by construction, with no comparison of fields. Rule 9 follows that reading, so an echo would clear the item's score, dismiss Berean and, under the automatic switch, start and pay for a fresh run on content that has not changed — which A7 rules out: *"A score on unchanged content never changes … users cannot abuse the re-review to force a new score or stack up costs for AI reviews."* The two answers:
   1. **An echo is a change, as §APR9.7.4 has it**, and Berean follows the round's dismissal. Nothing new is built. The cost is that an author can force a fresh run by re-saving under the automatic switch, as they already can by a one-character edit, which A7 admits.
   2. **Only a modify that changes a content field clears the score**, by the test §APR8.6.3 rule 3 already applies to the amender record. The flow cannot see which fields a modify changed, so each of the six foundations would have to tell it. That is a design change of its own, with a design task of its own.

   `Backend/Orchestrations/ApprovalOrchestrationService.BereanReview.md §2` (#1167) waits for the answer.
3. **Whether an offered round starts the confidence process without Berean being assigned.** Ruling 2 starts the process *"the moment something comes in that requires review"* wherever Berean is enabled, and A2 makes *enabled* `IsAIReviewerOffered = true`. A4 starts it when Berean is added as a reviewer, *"either manually or via ApprovalSetting.IsAIReviewerAutomaticallyRequested = true"*. On a tier with the offer on and the automatic switch off the two disagree: under ruling 2 a run starts when the round opens, and under A4 only when a person asks. Rule 4 follows A4, and nothing in the rulings says which is meant. `Backend/Orchestrations/AIReviewerOrchestrationService.BereanReview.md §2` (#1176) waits for the answer.
