# Approval interface — every approvable item carries a confidence score
Parent: [BereanReview.md](../../BereanReview.md)
Level: model — `IApproval` and `IConfidence` (`Glory2Him.Core/Models/Bases/`), the eight models that implement `IApproval` (`Glory2Him.Core/Models/Foundations/`), their storage configurations (`Glory2Him.Core/Brokers/Storages/Sql/StorageBroker.<Entity>.Configurations.cs`) and one migration. The Likes feature's work on the `Association` model is `Backend/Models/Association.md`.
Inherits: §APR9.7.1 rules 2 and 5, §APR13.4 rule 5, §ARC12.2.1, BereanReview.md rule 2, *Storage and migration* items 1 and 5, *What ships together* step 3

`IApproval` extends `IConfidence`, as the owner ruled on 2026-10-13: *"It is recorded against the entity that implements IApproval since IApproval implements IConfidence … Association must not implement IConfidence again since it is getting it via IApproval"* (BereanReview.md, A4). It reaches storage in two steps, because a column that exists before every add refuses the fields, and every modify keeps them as stored, would store whatever a caller sends: the model first, ignored by storage, and the columns once the six foundations keep a caller's copy out. Groundwork has no operation and no test paths of its own. Each section's proof is the build, CI's model checks, and §2's integration suite.

## 1. The model, not yet stored (#1154)

1. **`IApproval` is declared `public interface IApproval : IConfidence`**, its own members unchanged.
2. **`Association` drops `IConfidence` from its own list**, and keeps its four properties, which now implement the interface through `IApproval`. Its storage is unchanged.
3. **`ContentItem`, `Link`, `Tag`, `Reaction`, `Comment`, `BibleReference` and `Attachment` gain the four properties**: `decimal? ConfidenceScore`, `string? ConfidenceReason`, `Guid? SourceBatchId`, `string? ModelVersion`, each null by default.
4. **Storage ignores the four properties** in each of the seven configurations, so no column exists, no migration is added and nothing a caller sends is stored. §2 replaces each ignore with the column.
5. **`IConfidence`'s summary is not this section's.** Its words on a person's score — the human correction that must clear the provenance, and the two provenance fields' *"Null when a human set it by hand"* — are made untrue by `Backend/Foundations/AssociationService.BereanReview.md §1`, which refuses every person, and that section rewrites them (its rule 6), to say that only the system writes the four fields, that a score always carries its provenance, and that a null score means none has been recorded, or one was cleared because the content changed. This section makes none of the summary untrue, so it lands in either order with that one. `ConfidenceScore`'s own summary, which says that a null score never blocks and *"only an explicit zero does"*, is rewritten by `Backend/Clients/AccessClient.BereanReview.md §1` rule 6, because the low-score block makes it untrue first. *(This rule used to give the summary to this section, which therefore landed after that one.)*
6. **Until §2, a `$filter` or an `$orderby` naming one of the seven items' new properties fails** on a route that hands OData a query EF has yet to run, the items' `[EnableQuery]` routes among them: OData binds it, and EF has no column to translate it against. The request answers a server error. It reads nothing, writes nothing and discloses nothing, and §2 closes it, as `Backend/Models/IAmendment.md §1` item 4 accepts the same for its own property.
7. **The four fields are on every item's contract**, as an association's already are: every read that returns the item returns them, the anonymous public read of content items included (`/api/contentItems/Public`), because this section adds and removes no reader. That read's pinned shape records them: `BranchPointContentItemProperties` (`Websites/Glory2Him.WebApp.Tests.Acceptance/Apis/ContentItems/ContentItemTests.PayloadShape.cs`) gains `confidenceScore`, `confidenceReason`, `sourceBatchId` and `modelVersion`, as it gains `amenderUserIds` for the amender record (§APR8.6.3 rule 8, #996). Every read carries null until the review process writes a score (#1216). The owner ruled on 2026-10-15 that only the item's review tier reads the score and the reason, with their provenance, and that this section ships as designed (BereanReview.md R6, R8, rule 24): #1230 designs how every other reader is answered all four as null, and the review process's first write of a score waits for it (BereanReview.md, *What ships together* step 9), so this section withholds nothing.

## 2. The columns and their migration (#1196)

1. **`ContentItems`, `Links`, `Tags`, `Reactions`, `Comments`, `BibleReferences` and `Attachments` each gain** `ConfidenceScore decimal(4,2) NULL`, `ConfidenceReason nvarchar(500) NULL`, `SourceBatchId uniqueidentifier NULL` and `ModelVersion nvarchar(128) NULL`, mapped as `Associations` maps them (`StorageBroker.Association.Configurations.cs`), and a check constraint `CK_<Entity>_ConfidenceScoreRange` holding `ConfidenceScore IS NULL OR ConfidenceScore BETWEEN 0 AND 10`, as `CK_Association_ConfidenceScoreRange` does.
2. **One migration**: for each table, four nullable `ADD`s with no default and one `ADD CONSTRAINT`. Existing rows read null and nothing is updated, so the script is one batch with nothing to `EXEC`. No index — no reader filters on them.
3. **It waits for both rules on all six foundations**, the add's refusal and the modify's keeping of the stored fields — `Backend/Foundations/<Entity>Service.BereanReview.md §1` and `§2` for `ContentItem`, `Link`, `Tag`, `Reaction`, `Comment` and `BibleReference` — on `main`. `Attachment` has no foundation service and no write path that could carry them.
4. **Against §APR7.4 item 6's stage 2**, which adds `ApprovalId` to `IApproval` and to five of the same tables in one pull request (D1): whichever reaches `main` second generates its migration after the other's. Neither needs the other.
5. **It comes before the review process** (BereanReview.md, *What ships together* steps 4 and 5; designed under #1216): a score written to an item with no column is stored nowhere.
6. `Down` drops the columns and the constraints, for the developer's rollback alone. In effect the change is not reversible once a score is written, because dropping the columns loses it (BereanReview.md, *Risks*).
