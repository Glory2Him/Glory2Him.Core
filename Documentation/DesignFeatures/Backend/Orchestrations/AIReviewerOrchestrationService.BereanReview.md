# AI reviewer orchestration service — Berean's review
Parent: [BereanReview.md](../../BereanReview.md)
Level: orchestration — `IAIReviewerOrchestrationService` (`Glory2Him.Core/Services/Orchestrations/AIReviewers/`)
Inherits: §APR8.6.2, *Assignment*, §APR8.6.2.1, §ARC12.5 (entry 4, and *an orchestration holds brokers*), §EVN2, §EVN18(e), §EVN19 rules 1 and 4, §EVN23, §SEC14.6 rule 4, §SEC14.6.1, §SEC18.6 rule 2, BereanReview.md rules 3, 4, 8, 11, 18 and 19, *Layer placement* items 3–5

Berean's caller-facing lifecycle: a person's request and the review event it publishes, the withdrawal and its gate, and the status read. The service spans `Approval` and `AIReviewerAssignment`, two entity services, each a foundation, within two-to-three (§ARC12.5). It gains `IEventBroker`, to publish the review event, registered by the host. Its automatic assignment leaves it for the approval process (BereanReview.md, *Layer placement* item 4), and with it its two subscriptions on `Approval` facts. What answers the review event is the review process, designed under #1216.

## 1. RequestAIReviewerAsync — no re-request (#1162)

```csharp
ValueTask<AIReviewerAssignment> RequestAIReviewerAsync(
    EntityType entityType,
    Guid entityId,
    CancellationToken cancellationToken = default);
```

1. **Asking Berean onto a round whose live assignment is completed changes nothing**: it answers the standing row and writes nothing, as asking onto a pending one already does (BereanReview.md rules 4 and 8). It no longer resets a completed assignment to pending through `IAIReviewerAssignmentService.ModifyAIReviewerAssignmentAsync`, which this service then calls nowhere.
2. **Everything else is unchanged**: a round with no live assignment gets one, through the caller-facing add, under the caller's identity, gated on the resolved offer and an open round.
3. **The comment over `ValidateUserMayRequestAIReviewer`** stops saying *"an assignment sets nothing"*: an assignment holds the round shut until Berean's review has completed (BereanReview.md rule 11). The requesting tier still asks no HR-3 term, because asking Berean decides nothing — it moves the round only toward a block.
4. The interface's summary of the operation stops calling it *"asks it again once a prior assignment has completed"*.
5. **Every other text the re-request's removal makes untrue is rewritten with it** — the code's, its tests' and the React app's comments that describe asking Berean again, the reset it made, or the stale flags a moderator's ask cleared — so that none waits for a later task (`design.md`, *A gap that is built stays in its list*). A later task that removes or rewrites the same text again takes it as this section leaves it. The seam's paragraph on the re-request is among them (`Backend/Foundations/AIReviewerAssignmentService.md`, its opening rule). **The review panel's re-request control goes first** (`UI/Components/ReviewPanel.md` §10 item 16), and with it the panel's and its sample page's accounts of the server's upsert, which say that a completed assignment resets to pending: that removal lands before this section, so none of them is left for this section to make untrue.

## 2. RequestAIReviewerAsync — the review event (#1222)

1. **Once the request has run, the round's live assignment is read**, and where one stands, `AIReviewerOrchestration-Reviewing` is published once, carrying it (BereanReview.md rule 4; I6, I7). That holds whether the request has just added it or found it standing, pending or completed: a person who asks while Berean stands assigned publishes the event again (I7). It holds on the add's race too, where `UX_AIReviewerAssignments_ApprovalId` refuses the add because another request wrote the assignment in the same moment and the re-read answers that one (`AIReviewerOrchestrationService.Assignments.cs`): Berean stands assigned, so the event is published, carrying it. Where none stands — the add failed — nothing is published. The read is the one the request already makes, through `IAIReviewerAssignmentService.RetrieveAIReviewerAssignmentByApprovalIdAsync`, made again once the add has answered. **On a round that no longer offers Berean the request is refused**, as today, by the offer (`ValidateAIReviewerIsOffered`) before it reads the assignment, so it publishes nothing there though Berean stands assigned from before, and it removes nothing: removing Berean from such a round is the approval process's step 4 (BereanReview.md rule 9, step 4.3; R9).
2. **The event is minted under `IEventEnvelopeBroker.CreateSystemAsync`** (BereanReview.md rule 19): the review it asks for acts for nobody, though a person asked for Berean. The add stays under the caller's identity.
3. **This section mints the address.** `AIReviewerOrchestration-Reviewing` is a request address `AIReviewerOrchestrationService` owns, registered under stable identifiers in `EventBrokerIdentifiers.AIReviewerOrchestration.cs`, its content `AIReviewerAssignment`. Nothing subscribes to it until #1216 builds the review process, and publishing to it with no subscriber succeeds, as `Association-ConfidenceSet` is published today with none (§APR9.7.1 rule 5). The approval process's two publishes build on it (`Backend/Orchestrations/ApprovalOrchestrationService.BereanReview.md §7–§8`).
4. **A failed publish is logged and does not fault the request**, because the assignment it follows is written and the person's request has done what they asked: the round stays held by the pending block (BereanReview.md rule 11), and asking again publishes the event again (I7). **A cancellation is no failure of the publish**: an `OperationCanceledException` from it passes the step untouched and unlogged (`the-standard-cancellation-patterns`), and the service's own exception handling decides it (`AIReviewerOrchestrationService.Exceptions.cs`): one whose token was cancelled is rethrown as itself, unlogged, and one whose token was not — a timeout — faults the request with the orchestration's dependency exception, logged once. Either way the request answers no assignment, though Berean stands assigned, and asking again publishes the event again (I7). A failed add publishes nothing and faults as it does today.
5. **The service gains `IEventBroker`**, through its constructor, registered by the host. It is a broker of the kind an orchestration may hold, outside the two-to-three (§ARC12.5).
6. **The words that call a request on a standing assignment a no-op are rewritten**, in the code, its tests and the React app's comments: it writes nothing there, and publishes the review event (rule 1).
7. **A caller holding the global `ReadOnly` is refused before the request reads Berean's assignment**, so it neither adds one nor publishes the event. The read-only block refuses requesting Berean (§APR8.6.2, *Assignment*, B5), and where an assignment stands the publish is the request's only effect, which no foundation gate reaches: the foundation refuses the global name on its writes, and a request on a standing assignment writes nothing (`AIReviewerAssignmentService.Validations.cs`, `ValidateUserIsAllowedToContribute`). It is asked row-locally, from the security context the request already captures, ahead of the requesting tier, as every gate asks a block before a grant (§SEC18.6 rule 2), and it refuses with `UnauthorizedAIReviewerOrchestrationException` and the sentence the foundation's add refuses that caller with, *"The current user is blocked from managing AI reviewer assignments."* So where no assignment stands, that caller is refused here before the add is asked, where the add refused them before. The status read and the withdrawal do not ask it here: the read is no write, and the withdrawal's one effect is the foundation's remove, which refuses the global name itself. **The scoped names of the block are not this section's**: until B5's build gathers them (§APR8.6.2, *Assignment*, not yet built), a caller in the requesting tier who also holds a scoped read-only role, and not the global `ReadOnly`, may ask for Berean, and so start its review, as they may add Berean today.

## 3. The write-back, moved to #1216 (#1177, closed)

Retired from this design. It heard the confidence process's answer on `ContentAnalysis-Scored` and recorded the score, Berean's comments and the completion (#1177, closed). The review process now does all of it (BereanReview.md rule 6), and #1216 designs it. `ContentAnalysis-Scoring`, `ContentAnalysis-Scored`, `ContentAnalysisRequest` and `ContentAnalysisResult` were never built. ## 4. WithdrawAIReviewerAsync — only before Berean's review starts (#1223)

```csharp
ValueTask<AIReviewerAssignment> WithdrawAIReviewerAsync(
    EntityType entityType,
    Guid entityId,
    CancellationToken cancellationToken = default);
```

1. **A withdrawal of a live assignment whose `IsAIReviewStarted` is `true` is refused**, with the service's validation exception and the message *"Berean's review has started, so Berean can no longer be withdrawn."* (BereanReview.md rule 18; I1.5c).
2. **A withdrawal on a round whose resolved policy asks for Berean automatically is refused**, with the message *"This round's policy asks for Berean automatically, so Berean is removed only by changing the policy."* The automatic request is the resolved `AIReviewerPolicyVerdict.IsAutomaticallyRequested`, read through `IAccessBroker.ResolveAIReviewerPolicyByIdAsync` — `IsAIReviewerOffered && IsAIReviewerAutomaticallyRequested`, with the round requiring review (`Backend/Clients/AccessClient.BereanReview.md §3`). So a policy whose offer is switched off lets an assignment made under it be withdrawn, as the withdrawal's own summary requires (*"taking Berean off a round is the one act that has to keep working after the switch closes"*). (I2.B)
3. **Otherwise the withdrawal is unchanged**: it soft-deletes the live assignment under the caller's identity, and nothing standing is a no-op. It changes no tracking field and no score (BereanReview.md rule 18). Its read of the assignment is the one it makes today, through `IAIReviewerAssignmentService.RetrieveAIReviewerAssignmentByApprovalIdAsync`.
4. **Rule 1 is asked before rule 2**, so a started review is refused for being started whatever the policy says.
5. **The operation's summary** stops calling the withdrawal *"Unconditional, unlike the human withdrawal"*, and says what it now refuses.

## 5. OnApprovalAddedAsync, retired (#1226)

The automatic assignment's subscription on `Approval-Added` goes: the subscription, its accepted name and identifiers, the handler and its tests. The approval process's step 4 on an add assigns Berean in its place (`Backend/Orchestrations/ApprovalOrchestrationService.BereanReview.md §7`), and must be on `main` first (BereanReview.md, *What ships together* step 7). The private body both subscriptions share stays until §6 retires the other. **The words the retirement makes untrue are rewritten with it** (`design.md`, *A gap that is built stays in its list*): wherever the code, its tests or the design count two subscriptions, or name the one on `Approval-Added` among what stands, each says that one is left, on `Approval-Modified` — among them §APR8.2's `IsAIReviewerAutomaticallyRequested` row, which names the approval process's step 4 beside it as a reader of the verdict, and §APR8.6.2 setting 3's list of what *"all exist"*.

## 6. OnApprovalModifiedAsync, retired (#1227)

The automatic assignment's subscription on `Approval-Modified` goes, as §5's goes, after the approval process's step 4 on an update (`Backend/Orchestrations/ApprovalOrchestrationService.BereanReview.md §8`) is on `main`. With it go the body both shared (`AIReviewerOrchestrationService.Substrate.cs`), the six gates' code, and the comment over the two subscriptions in `EventSubscriptionRegistration.cs`. **Two dependencies leave the constructor with it**, because that body is their only caller: `IAIReviewerAssignmentWorkflowService`, whose automatic add the approval process now calls through the seam it holds, and `IEnvelopeIntegrityBroker`, which verified the two facts' envelopes. `IEventEnvelopeBroker` stays, for §2. The entity-service count is unchanged: the seam shares the foundation class's arm with `IAIReviewerAssignmentService` (§ARC16.7.1 finding 2). **The words it makes untrue are rewritten with it**, as §5's are: §APR8.2's row and §APR8.6.2 setting 3 say that the approval process's step 4 consumes the verdict and that both subscriptions are retired, setting 3 still naming the presence check until `Backend/Brokers/AccessBroker.BereanReview.md §7` retires it.
