# Access client — the confidence suggestion
Parent: [PostModeration.md](../../PostModeration.md)
Level: client — `IAccessClient` (`Clients/SecurityClients/G2H.Security.Client/Clients/Access/IAccessClient.cs`), `securityClient.Access`, the pure decision function of §APR8.6.1 rule 2, served by `AccessService`. The amender record's work on the same client is `Backend/Clients/AccessClient.md`.
Inherits: §APR8.4, §APR8.6.1 rules 2, 4 and 5, §APR8.6.2 (*The thresholds*; *The confidence suggestion* rules 1–6), §SEC14.7 posture A′ rules 2 and 3, posture D rule 2; `PostModeration.md` rule 13

The client decides the confidence suggestion and gathers nothing. `AccessBroker` hands it the entity's score, the round's role subjects, the actor, and the round's candidate policy rows with its policy key (`Backend/Brokers/AccessBroker.PostModeration.md §1`). It resolves which tier governs the round from those rows, as every decision of its does (§APR8.4), and reads that tier's pair. Every member of the request is `required`, so a forgotten gather is a compile error rather than an empty list read as permission (§APR8.6.1 rule 2).

**A new operation, not a widening of `ResolveAIReviewerPolicyAsync`.** `AIReviewerPolicyVerdict` leaves the thresholds out because *"nothing that resolves this verdict casts a vote or reads a score"*, and that stays true: none of its readers reads a score (`Backend/Clients/AccessClient.BereanReview.md §3` rule 2 lists them). The suggestion also depends on who asks (§APR8.6.2 suggestion rule 6), and that verdict is the same whoever asks: `IAccessBroker.ResolveAIReviewerPolicyByIdAsync` resolves it from the round alone, with no security context, and the approval process's step 4 reads it for writes that are the system's own (`DesignFeatures/BereanReview.md` rules 9 and 19). Carrying the suggestion there would give an actor-independent verdict an actor.

**It stays one operation.** Its logic is eight criteria, within the gate: the band's three outcomes and its comparisons proven as one rule (§1 rule 5) with cases, the governing tier's resolution and the fail-closed pair one each, three on who is answered it, one on the switches, and one on a missing score. The band (suggestion rule 1) and who is answered it (rule 6) are one answer: splitting them would hand the band to a caller before anything decided they may see it. This is the shape `MayRecordApprovalReviewAsync` takes, deciding the veto, the tier, HR-1 and the window in one call.

## 1. ResolveConfidenceSuggestionAsync (#1105)

```csharp
ValueTask<ConfidenceSuggestionVerdict> ResolveConfidenceSuggestionAsync(
    ResolveConfidenceSuggestionRequest resolveConfidenceSuggestionRequest);
```

1. **`ResolveConfidenceSuggestionRequest`** carries, each `required`: `Actor` (`AccessActor`), `RoleSubjects` (`IReadOnlyList<RoleSubject>`), `ConfidenceScore` (`decimal?`), `CandidatePolicies` (`IReadOnlyList<ApprovalPolicy>`), and the policy key `EntityType` (`string`), `ContentType` (`string?`) and `IsPersonal` (`bool?`), as `ApprovalConditionsRequest` carries them. The client resolves the governing tier from them (§APR8.4), and the pair it reads is that tier's `AIApprovalConfidenceRejectionThreshold` and `AIApprovalConfidenceApprovalThreshold` (§APR8.6.2 suggestion rule 1). Where no candidate resolves, the fail-closed default's `0.00`/`0.00` is read (suggestion rule 3).
2. **`ConfidenceSuggestionVerdict`** carries one member, `Suggestion`, of the new enum `ConfidenceSuggestion?` — `Approval = 1`, `Rejection = 2`, `Unable = 3`, with no zero member, so a default value is never read as a band. `null` is *no suggestion*.
3. **The actor is asked first.** An actor outside the review tier composed from `RoleSubjects` is answered no suggestion, whatever the score (§APR8.6.2 suggestion rule 6). The tier is the one `MayRecordApprovalReviewAsync` asks, one matching subject admitting. A read-only role does not withhold it (§SEC14.7 posture A′ rule 3), so the veto is not asked.
4. **A null `ConfidenceScore` answers no suggestion** (suggestion rule 2).
5. **The band is §APR8.6.2 suggestion rule 1's**, read strictly against the resolved pair: `Rejection` below the rejection threshold, `Approval` above the approval threshold, and `Unable` otherwise, between them or on either.
6. **No switch is read.** Neither the resolved `IsAIReviewerOffered` nor `IsAIAllowedToVote` is asked, so neither can govern the answer (suggestion rule 4); only the resolved tier's two thresholds are read from it.
7. **Validation:** a null request, and a null `Actor`, `RoleSubjects` or `CandidatePolicies`, is refused with the validation exception the client's other requests are refused with, naming the member; and so is a null, empty or blank `EntityType`, as `ValidateOnEvaluateApprovalConditions` and `ValidateOnResolveAIReviewerPolicy` refuse it (`AccessService.Validations.cs`), since a blank key matches no tier but the global one and the band would be read against the wrong pair with nothing refused. The client does not check the pair's scale or order: the columns' check constraints and `ApprovalSettingService`'s validations hold both on every stored row (§APR8.6.2, *The thresholds*), and the fail-closed pair is in order.
